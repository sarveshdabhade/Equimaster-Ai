1. EXECUTIVE SUMMARY
================================================================================

Equimaster-AI is a production-grade financial intelligence platform that
combines deep learning, natural language processing, and real-time market
data to provide actionable investment insights. The system is built on a
modular architecture supporting:

• LSTM-based multi-horizon price prediction (Day: 1, Week: 5, Month: 22, Quarter: 88 sessions)
• FinBERT-powered sentiment analysis from verified news sources
• Real-time market snapshots (6 major indices, 49+ stocks)
• Hybrid RAG (Retrieval-Augmented Generation) with FAISS embeddings
• Automated daily data refresh and model retraining pipeline
• Interactive Streamlit dashboard with 5-tab analysis interface
• Immutable prediction contracts for reproducible backtesting

Platform operates on Windows 10+ with Python 3.10+ and leverages:
- TensorFlow/Keras for deep learning
- FAISS/Sentence-Transformers for semantic search
- yfinance for market data
- NewsAPI.org + Yahoo Finance for news ingestion
- Streamlit for interactive UI

Current Status: 49 LSTM models trained across 4 horizons (229 total models),
100% test coverage for news validation, live deployment on localhost:8502

4.2 NEWS ACQUISITION & PROCESSING
───────────────────────────────────

Step 1: Fetch Articles
  ├─ Primary Source: NewsAPI.org
  │   ├─ Endpoint: /v2/everything?q={ticker}&domains={whitelist}
  │   ├─ Whitelist: 14 trusted publishers
  │   │   └─ reuters.com, bloomberg.com, cnbc.com, ft.com, wsj.com,
  │   │      economictimes.indiatimes.com, moneycontrol.com, mint.com,
  │   │      business-standard.com, thehindubusinessline.com,
  │   │      businesstoday.com, ndtv.com, finance.yahoo.com
  │   ├─ Limit: 8 articles per ticker
  │   ├─ Rate: 0.1s delay between tickers (anti-throttle)
  │   └─ Response: {title, summary, content, source, url, publishedAt}
  │
  ├─ Fallback: Yahoo Finance (.news endpoint)
  │   ├─ When: NewsAPI unavailable or rate-limited
  │   ├─ Returns: Minimal article metadata
  │   └─ Used for: Fallback only (not primary)
  │
  └─ Cache:
      ├─ TTL: 1 hour (NEWS_CACHE_TTL_HOURS)
      ├─ Storage: data/news_cache/{TICKER}.json
      └─ Force refresh: fetch_ticker_articles(ticker, force_refresh=True)

Step 2: Validate Article Sources
  ├─ Function: _is_trusted_article() [src/news/fetcher.py]
  ├─ Check: Article URL hostname against TRUSTED_NEWS_DOMAINS
  ├─ Validation: Strict whitelist (rejects synthetic/unverified)
  └─ Result: Only verified publishers included in sentiment

Step 3: Normalize Article Format
  ├─ Function: normalize_article() [src/news/fetcher.py]
  ├─ Standardize fields: title, summary, content, source, url, published_at
  ├─ Add metadata: ticker, published_timestamp (Unix epoch)
  └─ Output: dict with uniform schema

Step 4: Chunk Articles for Retrieval
  ├─ Function: chunk_article() [src/news/chunker.py]
  ├─ Chunking strategy:
  │   ├─ Concatenate: title + summary + content
  │   ├─ Split: 500 tokens per chunk, 120 overlap
  │   ├─ ID: SHA-1(url:index:chunk_text) - Prevents duplicates
  │   └─ Metadata: Preserved article fields per chunk
  │
  └─ Output: List of chunks
      ├─ chunk_id (hash)
      ├─ chunk_text
      ├─ chunk_index
      └─ Original article metadata

Step 5: Index & Retrieve Relevant Chunks
  ├─ Function: NewsRetriever.retrieve() [src/news/retriever.py]
  ├─ Filters:
  │   ├─ Recency: Only articles from last 2 days
  │   └─ Timezone handling: Convert UTC "Z" suffix to datetime
  │
  ├─ Primary: FAISS Embedding Retrieval
  │   ├─ Model: sentence-transformers/all-MiniLM-L6-v2
  │   ├─ Embedding dim: 384
  │   ├─ Index type: FlatL2 (exhaustive search)
  │   ├─ Query: "{ticker} {query_pattern}"
  │   ├─ k: top_k=5 most relevant chunks
  │   └─ Index persistence: data/.cache/news/embeddings/
  │       ├─ faiss.index (binary)
  │       └─ metadata.json (document mapping)
  │
  └─ Fallback: TF-IDF + Cosine Similarity
      ├─ When: FAISS unavailable (graceful degradation)
      ├─ Vectorizer: TfidfVectorizer(ngram_range=(1,2), max_features=1000)
      ├─ Similarity: cosine_similarity(query_vec, doc_vecs)
      ├─ Score normalization: [0, 1] range
      └─ Top k returned

Output: Retrieved chunks with relevance scores [0, 1]


4.3 SENTIMENT ANALYSIS PIPELINE
────────────────────────────────

Step 1: Score Articles with FinBERT
  ├─ Model: ProsusAI/finbert (pre-trained on financial text)
  ├─ Training data: 4.3B financial domain tokens
  ├─ Input: Article title + summary + content (concatenated)
  ├─ Output: Score in [-1, 1]
  │   ├─ Negative: < -0.15
  │   ├─ Neutral: [-0.15, 0.15]
  │   └─ Positive: > 0.15
  │
  ├─ Inference: model(text) → logits → softmax → score
  │   ├─ Classes: 0 (negative), 1 (neutral), 2 (positive)
  │   ├─ Score: P(positive) - P(negative)
  │   └─ Range normalized: [-1, 1]
  │
  └─ Fallback (if FinBERT unavailable):
      ├─ Keyword-based scoring
      ├─ High-impact terms: earnings, profit, growth, surge, soar
      ├─ Medium-impact: strong, weak, concern, challenge
      └─ Score: (high_hits * 0.35 + medium_hits * 0.2 + magnitude * 0.3)

Step 2: Aggregate Scores with Source Weighting
  ├─ Per-article adjustment:
  │   ├─ Base score (from FinBERT)
  │   ├─ Relevance multiplier: score * (0.7 + relevance * 0.3)
  │   └─ Source weight: Reuters/Bloomberg/FT = 1.1, others = 1.0
  │
  ├─ Portfolio aggregation:
  │   ├─ Weighted calculation:
  │   │   weighted_score[i] = score[i] * source_weight[i] *
  │   │                        (0.55 + relevance[i] * 1.2)
  │   ├─ Overall: mean(weighted_scores), clamped [-1, 1]
  │   └─ Confidence: 0.5 + abs(overall_score) * 0.7
  │
  └─ Label assignment (5 categories):
      ├─ Bullish: score > 0.25 AND positive_ratio > 0.6
      ├─ Bearish: score < -0.25 AND negative_ratio < 0.4
      ├─ Risk-off: score < -0.25 AND negative_ratio > 0.6
      ├─ Mixed: Positive AND negative signals present
      └─ Neutral: Default fallback

Step 3: Generate Evidence Attribution
  ├─ For each article in sentiment calculation:
  │   ├─ Title, source, published_at
  │   ├─ Sentiment score + classification
  │   ├─ Confidence level
  │   ├─ Source weight applied
  │   ├─ Relevance score (from RAG)
  │   └─ Impact level (High/Medium/Low)
  │
  └─ Drivers extraction:
      ├─ If positive_count > 0: "earnings and demand tailwinds"
      ├─ If negative_count > 0: "execution and risk concerns"
      └─ Else: "limited fresh catalysts"

Output: Comprehensive sentiment record
  {
      "ticker": str,
      "overall_score": float [-1, 1],
      "label": str,
      "confidence": float [0, 1],
      "articles": [scored articles],
      "evidence": [attribution records],
      "drivers": [reasons],
      "summary": str
  }

5. MACHINE LEARNING MODELS & TRAINING
================================================================================

5.1 LSTM ARCHITECTURE
──────────────────────

Model Type: Multi-Horizon LSTM (4-output Sequential)

Architecture Diagram:

  INPUT LAYER: (60, 21)
      │
      │ 60-day window × 21 features
      │ (OHLCV + 15 technical indicators)
      │
      ▼
  LSTM LAYER 1: 50 units, return_sequences=True
      │
      │ Captures temporal dependencies
      │ Return full sequence for next layer
      │
      ├─→ Hidden state: 50-dim
      └─→ Cell state: 50-dim (memory)
      │
      ▼
  DROPOUT: 0.2 (20% units randomly zeroed)
      │ Prevents overfitting
      │
      ▼
  LSTM LAYER 2: 50 units, return_sequences=False
      │
      │ Final temporal processing
      │ Return only last output (summary vector)
      │
      ├─→ Hidden state: 50-dim
      └─→ Cell state: 50-dim
      │
      ▼
  DROPOUT: 0.2
      │
      ▼
  DENSE LAYER: 25 units, activation='relu'
      │
      │ Feature extraction for decision layer
      │
      ▼
  OUTPUT LAYER: 4 units, activation='linear'
      │
      └─→ [pred_1day, pred_5day, pred_22day, pred_88day]
          (Normalized closing prices for 4 horizons)

Code:
  Sequential([
      Input(shape=(60, 21)),
      LSTM(50, return_sequences=True),
      Dropout(0.2),
      LSTM(50, return_sequences=False),
      Dropout(0.2),
      Dense(25, activation='relu'),
      Dense(4)  # 4 horizons
  ])
  model.compile(optimizer='adam', loss='mse')


5.2 TRAINING CONFIGURATION
──────────────────────────

Hyperparameters:
  ├─ Optimizer: Adam (lr=0.001 default)
  ├─ Loss: Mean Squared Error (MSE)
  ├─ Epochs: 10 (configurable)
  ├─ Batch size: 32
  ├─ Validation split: 0.2 (20% holdout)
  ├─ Early stopping: Not implemented (fixed epochs)
  └─ Callbacks: TensorBoard logging (optional)

Workflow:
  1. Load training data: X_train shape (1950, 60, 21), y_train (1950, 4)
  2. Fit model: model.fit(X_train, y_train, epochs=10, batch_size=32,
                           validation_split=0.2, verbose=0)
  3. Evaluate: Compute MSE on validation set
  4. Save: model.save("models/lstm_{TICKER}.keras")
  5. Predict: y_pred = model.predict(X_test)
  6. Denormalize: scaler.inverse_transform(y_pred)
  7. Log metrics: {ticker, mae, rmse, directional_accuracy}

Training Time:
  ├─ Per ticker: ~30-60 seconds
  ├─ All 49 tickers: ~25-50 minutes (sequential)
  ├─ Parallelization: 4-6 workers available (multi-threading)
  └─ Full pipeline (download → preprocess → sequence → train): ~90 mins


5.3 PREDICTION GENERATION
──────────────────────────

At Runtime (Stock Analyzer → LSTM Tab):

  1. Load artifacts:
      ├─ scaler: joblib.load("data/train_data/scaler_{TICKER}.pkl")
      └─ model: tf.keras.models.load_model("models/lstm_{TICKER}.keras")

  2. Prepare input:
      ├─ Load processed data: data/processed/{TICKER}_processed.csv
      ├─ Take last 60 rows (most recent 60 days)
      ├─ Normalize using training scaler
      └─ Reshape: (1, 60, 21) for batch prediction

  3. Predict:
      ├─ y_pred = model.predict(X_test)  # Shape: (batch_size, 4)
      ├─ Each output: [pred_1day, pred_5day, pred_22day, pred_88day]
      └─ Values: Normalized [0, 1] range

  4. Denormalize:
      ├─ scaler.inverse_transform(y_pred)
      ├─ Convert back to original price scale
      └─ Output shape: (batch_size, 4) with real prices

  5. Compute signals:
      ├─ Current close: df['Close'].iloc[-1]
      ├─ Expected return: (pred_price - current) / current
      ├─ Direction: positive (+1), negative (-1), neutral (0)
      ├─ Magnitude: abs(return %)
      └─ Confidence: 0.3 + abs(return %) * 0.7  (capped at 0.99)

  6. Display:
      ├─ Plotly chart: Candlestick (actual) + Line (predicted)
      ├─ Table: Horizon, Current, Predicted, Return %, Direction
      └─ Metrics: MAE, RMSE, Directional Accuracy (on test set)


5.4 MODEL EVALUATION METRICS
──────────────────────────────

Test Set Performance (Last 20% of data):

  Mean Absolute Error (MAE):
      MAE = (1/n) * Σ |actual - predicted|
      ├─ Units: Price units (Rs)
      └─ Typical range: ±5-15% of stock price

  Root Mean Squared Error (RMSE):
      RMSE = sqrt((1/n) * Σ (actual - predicted)²)
      ├─ Penalizes large errors more than MAE
      └─ Typical range: ±8-20% of stock price

  Directional Accuracy:
      Accuracy = (1/n) * Σ sign(actual_return) == sign(predicted_return)
      ├─ Binary metric (match directions or not)
      ├─ Typical range: 45-60% (random = 50%)
      └─ Used for trading signal validation

  Mean Absolute Percentage Error (MAPE):
      MAPE = (1/n) * Σ |(actual - predicted) / actual|
      ├─ Percentage error
      └─ Typical range: 3-12%

Validation Strategy:
  ├─ Train/Test split: 80/20 by date (no lookahead bias)
  ├─ Test set: Last 504 trading days (~2 years)
  ├─ Metrics computed on test set only
  └─ No cross-validation (temporal series property)


5.5 MULTI-HORIZON PREDICTION STRATEGY
───────────────────────────────────────

Output 4 Predictions Simultaneously:

  Horizon      Trading Days   Calendar Days   Use Case
  ─────────────────────────────────────────────────────────────
  1-day        1              1               Day trading, risk alerts
  5-day        5              ~1 week         Short-term positions
  22-day       22             ~1 month        Medium-term investing
  Quarter      88 sessions    ~4 months       Existing long-horizon model

Advantage: Single model trained on 60-day window predicts 4 horizons
  ├─ Captures multiple trend lengths simultaneously
  ├─ Reduces training overhead (1 model vs 4 independent models)
  └─ Ensures consistency across horizons

Disadvantage:
  ├─ Increased output space → more difficult to learn
  ├─ Trade-off between accuracy across horizons
  └─ 1-day predictions less accurate than dedicated model

6.1 PREDICTION CONTRACT
───────────────────────

Immutable Record Design:

  @dataclass(frozen=True)
  class PredictionRecord:
      ticker: str                    # Stock symbol
      as_of: str                     # Date of prediction
      horizon: int                   # Day/Week/Month/Quarter (1, 5, 22, 88 sessions)
      current_close: float           # Price at prediction time
      predicted_close: float         # Forecasted price
      lstm_signal: float             # LSTM output [-1, 1]
      sentiment_score: float         # Sentiment [-1, 1]
      combined_score: float          # Fusion [-1, 1]
      combined_label: str            # Bullish/Bearish/Neutral

Benefits of frozen=True:
  ├─ Immutability ensures record integrity
  ├─ Enables reproducible backtesting
  ├─ Thread-safe for concurrent analysis
  └─ Prevents accidental mutation

Supporting Functions:

  def bounded_signal(value: float) -> float:
      """Clamp value to [-1, 1]"""
      return max(-1.0, min(1.0, value))

  def classify_signal(score: float, threshold: float = 0.05) -> str:
      """Classify signal:
          score > threshold:  "Bullish"
          score < -threshold: "Bearish"
          else:              "Neutral"
      """

  def directional_accuracy(predicted_return: float,
                          actual_return: float) -> float:
      """1.0 if signs match, else 0.0"""
      if (predicted_return * actual_return) > 0:
          return 1.0
      return 0.0


6.2 SIGNAL FUSION: TECHNICAL + SENTIMENT
──────────────────────────────────────────

Hybrid Scoring:

  1. Technical Signal (from LSTM):
      ├─ Input: Last 60 days of OHLCV + indicators
      ├─ Process: LSTM → normalized output [-1, 1]
      └─ Interpretation: -1 (strong sell), 0 (neutral), +1 (strong buy)

  2. Sentiment Signal (from FinBERT):
      ├─ Input: Recent news articles (last 2 days)
      ├─ Process: Article aggregation with source weighting
      └─ Output: [-1, 1] range

  3. Hybrid Combination:
      combined_score = 0.5 * lstm_signal + 0.5 * sentiment_score
      ├─ Equal weighting (configurable)
      ├─ Ensures both signals contribute equally
      └─ Output: [-1, 1] range

  4. Confidence Scaling:
      confidence = 0.3 + abs(combined_score) * 0.7
      ├─ Minimum: 0.3 (high uncertainty)
      ├─ Maximum: 1.0 (perfect agreement)
      └─ Used for position sizing in trading systems

10.4 ERROR HANDLING & RECOVERY
───────────────────────────────

Try-Except Patterns:

  def safe_yfinance_download(ticker):
      try:
          return yf.download(ticker, period="10y")
      except Exception as e:
          logging.error(f"yfinance failed for {ticker}: {e}")
          return None  # Graceful degradation

  def safe_newsapi_fetch(ticker):
      try:
          return _newsapi_articles(ticker)
      except Exception as e:
          logging.warning(f"NewsAPI failed: {e}, trying Yahoo fallback")
          return _yahoo_articles(ticker)

Resilience Features:
  ├─ Fallback sources: Yahoo Finance if NewsAPI fails
  ├─ Fallback metrics: TF-IDF if FAISS unavailable
  ├─ Partial failures: Pipeline continues if 1-2 tickers fail
  ├─ Caching: Stale data shown if fresh fetch fails
  └─ Logging: All errors logged to app_errors.log

Recovery Procedures:
  ├─ Timeout: 30s max per API call, retry 3× with backoff
  ├─ Rate limit: 429 responses → exponential backoff + sleep
  ├─ Connection error: Retry after 5s, max 3 attempts
  ├─ Model missing: Show error message, offer retrain option
  └─ Data corruption: Validate checksums, regenerate if needed
